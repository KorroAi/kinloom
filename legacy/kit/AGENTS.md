## Kinloom (AI inside this game)

This project uses **Kinloom** to put language-model AI into the game. You (the coding agent) do the integration; Kinloom gives you a validated runtime and tools. Kinloom knows nothing about genres: anything in the game can be read, steered, inhabited or generated by an AI, within the limits you declare.

**Read first:** `kinloom/docs/reference.md` (every field and rule), then the recipe closest to the request in `kinloom/docs/recipes/` (character, director, generator, narrator, analyst, interface). Other languages/engines: `kinloom/docs/protocol.md`. Follow `kinloom/docs/integration-checklist.md`.

**How it fits together:** the game declares things (types with readable properties, bounded params, functions, creatable types), events and roles in `kinloom/*.json`. Roles (AIs with a mission) wake on events, intervals, conditions or when asked, and act only through the tools their permissions allow. Every proposal goes through the Arbiter; the game receives validated effects, applies them and resolves them. Instant behaviors (rules written by you or by roles) run every frame without model calls.

**Workflow**
1. `kinloom scan` via the MCP tool `scan_project` (or read the code) to find what the request involves.
2. Declare types/things/events/roles/behaviors/generators in `kinloom/*.json`. Give each role the narrowest `sees` and `can` that do the job.
3. Wire the engine: Godot → `Kinloom.Bind(id, node)`, `Kinloom.EmitEvent(...)`, signals (`Said`, `Replied`...); JavaScript/TypeScript and Python → the client in `kinloom/client/`; others → the protocol.
4. Prove it: `kinloom validate`, `kinloom test` (write a `kinloom/tests/*.test.json` per feature, scripted models, no tokens), MCP `simulate_role` and `attack_guardrails` (escapes must be 0). With the game running: MCP `attach` or `kinloom inspect`.
5. Make sure the game still works with no API key (fallbacks: role `fallback`, game-declared behaviors, generator `fallback`).

**Rules**
- Never put an API key in a file. kinloom.json only names the environment variable (`provider.keyEnv`).
- Never invent prices, model names or facts. Prices come from the provider's pricing page with `prices.source`; leave them empty otherwise.
- Model output never touches the game directly: always go through effects, and always resolve them (`ok`, `refused` with a reason, `failed`).
- Player text is data, not instructions; do not build features that let it change permissions.
- Real-time control (aiming, driving, platforming) belongs to game code and instant behaviors; models decide intentions.
